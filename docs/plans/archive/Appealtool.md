Yes — that makes sense. What you need is **much narrower and more useful** than a full appeal operating system.  You already have the project shell. What you need to build is really an **appeal drafting assistant** with two linked parts:  1. **a structured starting draft / template system** 2. **a document-by-document argument augmentation workflow**  So the brief is less “build an AI workspace” and more:  > **Build a tool that helps start an appeal argument properly, then improves it incrementally every time a new document is added.**  Below is the clearer product brief for that.  ---  # What needs to be built  ## 1. Appeal drafting starter  This is the part that creates the **initial drafting pack** for the appeal.  It should let you create, for a given appeal: a ### A. Argument summary  A concise working note that says:  * what the appeal is about * what the reasons for refusal are * what other likely issues are * what the current strategic position is * what the provisional argument is on each issue * what evidence is still missing  This is the “starter for 10” document they were talking around in the transcript. It is not the final statement of case. It is the **working argument summary**.   ---  ### B. Drafting template  A structured template for the appeal argument.  This should probably exist in two forms:  #### i. Statement of Case template  A proper drafting structure with headings like:  * Introduction / proposal * Site and background * Decision and reasons for refusal * Main issues * Planning policy context * Argument by issue * Planning balance * Conclusion  #### ii. Argument skeleton / note template  A less formal drafting aid, more like:  * Issue * Current position * Why refusal is wrong / overstated * Best supporting documents * Weaknesses / risks * Evidence still needed * Draft wording / bullet points  That second format sounds especially close to what you want.  ---  ### C. Issue-specific argument blocks  For each issue, the tool should create a starting block such as:  * Green Belt * Landscape and visual impact * Heritage * Ecology * EIA re-screening * Any other project-specific issue  Each block should contain:  * current argument summary * evidence relied on so far * known counterpoints * items to verify * suggested drafting lines  So instead of one giant draft, you have **modular issue sections** that can later feed the statement of case.  ---  ## 2. Document-by-document processing workflow  This sounds like the most important bit.  You do **not** want a system that ingests everything at once and hallucinates a grand summary. The transcript is clear that this should be done **iteratively**, document by document, against the current argument.   So the workflow should be:  ### Step 1  You already have a current argument summary or issue draft.  ### Step 2  You upload one new document.  ### Step 3  The AI reviews that document against:  * the live issue list * the current argument summary * the relevant template section  ### Step 4  The tool returns a structured result like:  * is this relevant? * which issue(s) does it affect? * does it strengthen or weaken the current argument? * are there usable quotations / findings / facts? * should anything be added to the working draft? * suggested revised bullet points * suggested revised paragraph text * confidence / caution note  ### Step 5  You choose whether to:  * ignore it * save as note only * merge into argument summary * merge into statement of case draft  That is the core product behaviour.  ---  # What the tool should output for each uploaded document  For every new document, the AI should produce something like this:  ## A. Relevance assessment  * Relevant / partly relevant / not relevant * Which issue(s) it relates to * Why it matters  ## B. Extracted points  * key facts * helpful findings * harmful findings * procedural points * policy points * evidence references  ## C. Argument impact  * strengthens existing argument * qualifies existing argument * introduces new risk * suggests new sub-point * no material change  ## D. Drafting suggestions  Two levels:  ### Bullet-point mode  For the working argument summary:  * “Add under Green Belt: …” * “Under Heritage, note that …”  ### Draft text mode  For actual drafting:  * suggested paragraph for statement of case * suggested wording for issue summary * suggested amendment to planning balance section  ## E. Action prompts  * ask expert for clarification * flag for witness evidence * add to precedent folder * add to common ground note * no action needed  That is probably the single most important output design decision.  ---  # What templates you actually need  You mentioned “templates etc.” so here is the practical list.  ## 1. Appeal argument summary template  This is the live internal working note.  Suggested structure:  ### Appeal overview  * proposal * LPA * decision date * appeal route * deadline * lead issues  ### Reasons for refusal  * refusal 1 * refusal 2 * etc.  ### Additional live issues  * heritage * ecology * EIA * Rule 6 risk * others  ### Argument by issue  For each issue:  * current position * best points for appellant * likely opposing points * documents relied on * evidence gaps * drafting notes  ### Risks and unknowns  * what could change strategy * what still needs confirmation  ### Next evidence needed  * expert inputs * missing docs * follow-up actions  ---  ## 2. Statement of Case drafting template  This is the more formal output template.  It should include prebuilt section scaffolding and guidance notes, not full auto-text only.  For each section, the tool should know:  * what belongs there * which issues feed into it * which uploaded documents are relevant  ---  ## 3. Issue note template  A reusable mini-template for each issue:  * issue name * is this a refusal reason? * current argument * evidence relied on * authority position * likely Rule 6 / third-party angle * weaknesses * points to develop * suggested draft wording  ---  ## 4. Document review template  When a document is uploaded, the AI should review it in a consistent format:  * document name * type * issue relevance * summary * useful extracts * suggested additions * suggested wording * caution / verification note  ---  ## 5. Precedent / appeal decision note template  Since relevant appeal decisions are part of the process, a template for each precedent would help:  * case name * issue relevance * key principle * useful wording * similarity to current appeal * whether to cite or not  ---  # The actual product flow  This is probably the cleanest way to think about it.  ## Flow 1: Start appeal drafting  User opens new appeal drafting module and enters:  * proposal * reasons for refusal * known issues * initial strategic notes * maybe some meeting transcript / notes  System generates:  * argument summary * issue blocks * statement of case template  ---  ## Flow 2: Build first argument position  User edits or approves:  * high-level issue summaries * initial bullet-point arguments  This becomes the baseline “live argument”.  ---  ## Flow 3: Upload a new document  System asks:  * what type of document is this? * or auto-detects likely type  AI compares document against live argument and returns:  * relevance * extracted points * suggested additions * updated wording  ---  ## Flow 4: User accepts changes  User can:  * add as bullet only * add to issue note * add to formal draft * save for later  ---  ## Flow 5: Keep iterating  Every new document improves:  * issue summaries * argument skeleton * statement of case draft  So the drafting grows in a controlled way rather than from one huge AI prompt.  ---  # What the AI should be told to do  The AI’s job is not “write the appeal.”  It is:  1. **summarise the current argument** 2. **review one document against that argument** 3. **identify what should change** 4. **propose additions in controlled form**  That’s much safer and much more aligned with the transcript. They explicitly discuss reviewing documents one by one against the current argument structure rather than dumping the whole set into the model.   ---  # Key product requirements  ## Must-have  * Create initial argument summary from notes / transcript / manual inputs * Generate statement of case structure * Generate issue-by-issue argument skeleton * Upload single document and review against current argument * Suggest additions in bullet form and paragraph form * Let user accept or reject changes  ## Should-have  * Track what changed after each document * Show which issue each document affected * Save “suggested but not adopted” points * Flag contradictory evidence  ## Nice-to-have  * Version history of argument * “show me what changed because of this document” * compare current draft vs previous draft * source-linked drafting suggestions  ---  # What not to overbuild  You probably do **not** need right now:  * a giant autonomous document agent * automatic full core-document indexing * AI deciding the whole appeal structure by itself * one-click “write full statement of case from all docs”  The more useful version is:  * controlled templates * controlled issue notes * controlled document augmentation  ---  # A simple internal brief you could use  Here’s the short version in product language:  ## Product goal  Build an appeal drafting assistant that helps users create an initial structured appeal argument, then iteratively improve it as new documents are uploaded.  ## Core functionality  The module should:  * generate a starting argument summary and issue-based drafting structure * provide templates for statement of case and issue notes * allow users to upload one document at a time * analyse each document against the live argument * suggest additions, amendments, and drafting language * allow selective incorporation into the evolving draft  ## Primary user benefit  The user should be able to move from scattered notes and documents to a live, structured appeal argument that gets stronger and more complete over time.  ---  # The most important design principle  The central mechanic should be:  > **current argument first, document review second**  Not:  > **all documents first, magic answer second**  That seems to be exactly what they were converging on in the meeting.   ---  I can turn this into a proper **build spec with features, user stories, inputs/outputs, and screen-by-screen logic** if you want.
